# Spec-builder — אפיון + פרומפט בוט אוטומטי

הרחבה של תהליך העיבוד: אחרי התמלול, לפי **סוג הפגישה שבכותרת הזום**, המערכת מייצרת
אוטומטית מסמכים ומפיצה אותם ליעדים שונים.

```
תמלול (קיים) → summarize (קיים)
                     │
                     ▼  spec_stage — מסתכל על שם הפגישה
                     │
   ┌─────────────────┴──────────────────┐
   │ "הדגמה" / "התאמה"                   │ "פגישת אפיון" / "הטמעה"
   ▼                                    ▼
 מסמך אפיון מפגישת הדגמה              ├─ מסמך אפיון → PDF ממותג → הערת GHL
 → PDF ממותג → הערת GHL               └─ פרומפט בוט + בסיסי ידע → Google Drive
```

## פגישת הדגמה → מסמך אפיון לקוח

פגישת ההדגמה היא השיחה הראשונה עם לקוח פוטנציאלי, ובה **נאמר ללקוח הכל בקול**: המחיר
החודשי, השנתי, מה עולה עם התחייבות לשלושה חודשים ומה בלעדיה, וכמה שעות הקמה. לכן המסמך
הזה **מצטט מחירים מהתמלול ואינו מחשב אותם** — אין מנוע תמחור בקוד, וכל מספר שנכנס
למסמך נאמר בפגישה. (הטמעה רגילה = 10 שעות; זה הנתון היחיד שהפרומפט מכיר כברירת מחדל.)

מה המסמך כולל: פרטי הלקוח, נתוני העסק ככרטיסי KPI, המצב היום, הבעיות, המטרות, הפתרון,
מה מקימים בפועל, גבולות היקף, אחריות הלקוח, תמחור (שני כרטיסים — רגיל ומומלץ),
ולוחות זמנים.

בנוסף ל-PDF, ההערה ב-GHL נושאת שני דברים שלא נכנסים למסמך שהלקוח רואה:
- **תיקוני שמות** שבוצעו אוטומטית (למשל "מורנית → אורנית").
- **טעון בדיקה לפני התחייבות** — חיבורי API, סקרייפינג ושליחה המונית שהוצגו בפגישה
  אך לא אומתו טכנית.

הקוד: `is_demo_meeting()` + `build_demo_spec_and_deliver_to_ghl()` ב-`tasks/spec_stage.py`,
והפרומפט ב-`services/spec_client.py::DEMO_SPEC_SYSTEM_PROMPT`.

## מה נכנס להערות ומה לקבצים

הכלל: **ההערות (Notes) בכרטיס הלקוח נושאות רק את הסיכום.** כל מסמך ארוך — תמלול,
אפיון — נשמר כקובץ בשדה קובץ בכרטיס, וההערה רק מפנה אליו.

| תוכן | איפה |
|---|---|
| סיכום הפגישה | הערה בכרטיס |
| תמלול — **פגישת הדגמה** | קובץ PDF → שדה **"תמלול מלא של שיחת המכירה"** + קישור בהערה |
| תמלול — כל פגישה אחרת | קובץ PDF במדיה + קישור בהערה (בלי הצמדה לשדה) |
| אפיון מפגישת הדגמה | קובץ PDF → שדה **"אפיון מהשיחת מכירה"** + קישור בהערה |
| אפיון מפגישת אפיון | קובץ PDF → שדה **"מסמך אפיון"** + קישור בהערה |
| פרומפט בוט | קובץ PDF → שדה **"פרומפט בוט"** + הטקסט בהערה |
| תיקוני שמות · טעון בדיקה | הערה בכרטיס (לא נכנס למסמך שהלקוח רואה) |

שדות הקובץ הם **custom fields מסוג FILE_UPLOAD** ומאותרים לפי שם בזמן ריצה, בלי id
מקודד. אם שדה לא קיים ב-GHL הקובץ עדיין מועלה למדיה והקישור נכנס להערה.

> **למה לא מצמידים כל תמלול לשדה:** שדה קובץ מחזיק **ערך אחד**. אילו כל פגישה הייתה
> נכתבת לאותו שדה, פגישת תמיכה מחודש הבא הייתה דורסת את תמלול שיחת המכירה שעליה
> נסגרה העסקה. לכן השדה שמור לשיחת המכירה בלבד — כפי ששמו מעיד — וכל שאר התמלולים
> נגישים דרך הקישור בהערת הסיכום שלהם.

**נפילה-לאחור:** אם העלאת הקובץ נכשלת, התוכן חוזר לצורתו הישנה כהערה (התמלול מתפצל
להערות של 65k תווים) — עדיף כרטיס עמוס מתמלול שלא קיים בשום מקום.

> ⚠️ **תלות חיצונית:** פרויקט האווטר (`~/pain-mining/fetch_notes.py`) שולף תמלולים
> לפי ההערה "📝 תמלול מלא". משהתמלול עובר לקובץ, השליפה הזו תמצא רק פגישות ישנות —
> צריך לעדכן אותו לקרוא את שדה הקובץ.

## מה מיוצר ולאן

| תוצר | יעד | שם הקובץ |
|------|-----|----------|
| מסמך אפיון (PDF ממותג) | תיקיית הלקוח ב-Drive + קישור בהערת GHL | `{לקוח} - פגישת אפיון - {תאריך}.pdf` |
| טקסט האפיון | גוף הערת GHL על כרטיס הלקוח | — |
| פרומפט בוט | תיקיית הלקוח ב-Drive (Google Doc) | `{לקוח} - בוט - {תאריך}` |
| בסיסי ידע | תת-תיקייה "בסיסי ידע" של הלקוח (Doc לכל בסיס) | `{שם הבסיס}` |

מבנה ב-Drive (מתחת ל-`GDRIVE_PARENT_FOLDER_ID`):
```
{לקוח}/
  {לקוח} - פגישת אפיון - {תאריך}.pdf
  {לקוח} - בוט - {תאריך}            ← Google Doc
  בסיסי ידע/
    {בסיס 1}, {בסיס 2}, ...          ← Google Doc לכל אחד
```

## שני מצבי הפעלה

1. **אוטומטי** — כל פגישת אפיון/הטמעה שעוברת בתהליך העיבוד מייצרת את התוצרים לבד.
2. **ידני** — דף אינטרנט: `https://<server>/spec/ui?token=<SPEC_UI_TOKEN>`
   מציג פגישות אחרונות (אפיון/הטמעה מסומנות), וכפתור "צור מסמכים" לכל אחת.

הכל **best-effort**: אם הפקת האפיון/הדרייב נכשלת, תהליך התמלול→סיכום→הערה הרגיל לא נשבר.

## משתני סביבה חדשים (Render → service env)

| משתנה | תיאור |
|-------|-------|
| `GOOGLE_CLIENT_ID` | OAuth client id של אפליקציית Google |
| `GOOGLE_CLIENT_SECRET` | OAuth client secret |
| `GOOGLE_REFRESH_TOKEN` | refresh token לחשבון של אורנית (ראה למטה) |
| `GDRIVE_PARENT_FOLDER_ID` | ה-id של תיקיית האב ב-Drive של אורנית |
| `SPEC_UI_TOKEN` | סוד להגנת דף ההפעלה הידנית (המצא מחרוזת אקראית) |

בלי משתני ה-Google, האפיון עדיין ייכתב כטקסט בהערת GHL — רק ההעלאה ל-Drive והקישור ל-PDF ידלגו.

## הפקת הרשאת Google (פעם אחת)

1. ב-[Google Cloud Console](https://console.cloud.google.com): צור פרויקט → הפעל **Google Drive API**.
2. צור **OAuth client id** מסוג **Desktop app** → הורד `client_secret.json`.
3. מקומית, מחוברת לחשבון **Oranitmorethan@gmail.com**:
   ```
   pip install google-auth-oauthlib google-api-python-client
   python server/scripts/google_oauth_setup.py client_secret.json
   ```
   אשר בדפדפן — הסקריפט ידפיס `GOOGLE_CLIENT_ID/SECRET/REFRESH_TOKEN`.
4. ב-Drive, צור תיקיית אב (למשל "לקוחות — אפיון ובוטים"), פתח אותה, וה-id נמצא ב-URL
   (`.../folders/<זה ה-id>`). הכנס ל-`GDRIVE_PARENT_FOLDER_ID`.
5. הזן את כל הערכים ב-Render → **Manual Deploy** / redeploy.

## פריסה

`git push` → Render בונה מחדש (autoDeploy). ה-Dockerfile מתקין Chromium ל-Playwright
(`playwright install --with-deps chromium`) — הבנייה הראשונה ארוכה יותר (~2–3 דקות נוספות).

